# 자동 감시와 알림 운영

Phase 6 구현 기록입니다. 실제 외부 서비스 배포와 전체 수신 검증은 Phase 7에서 진행합니다.

## 적용과 비밀값

프로젝트 루트에서 새 DB 구조를 적용합니다.

```bash
.venv/bin/alembic upgrade head
.venv/bin/alembic current
```

`0006 (head)`가 최신입니다. `0006`은 알림 작업 소유 토큰, 오픈 일정 버전, 정책 규칙 비교값과 고유 제약을 추가합니다. 이 단계에서 실제 Supabase에는 적용하지 않았습니다.

GitHub 저장소의 Actions Secrets에는 `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`을 등록합니다. 사용자별 목적지는 DB의 `telegram_users.chat_id`를 사용합니다. `TELEGRAM_CHAT_ID`는 기존 단일 목적지 코드와의 호환용 선택 값입니다. 정기 수집 작업에 LLM 키는 필요하지 않습니다.

## 잔여석 감시

아직 구독이 없어 수집 대상이 0이라면 로컬에서 직접 등록할 수 있습니다.

```bash
.venv/bin/tenniswatch link-telegram
.venv/bin/tenniswatch subscribe-gangseo --date 2026-10-26 --start-time 18:00 --end-time 22:00
```

첫 명령은 웹훅 충돌을 미리 검사하고 본인 봇 주소와 확인 문구를 표시합니다. 터미널을 켜 둔 채 3분 안에 한 줄 전체를 해당 봇에 보내면 개인 채팅을 확인하고 `.env`에 저장하며 봇에서도 완료 답장을 보냅니다. 대기 상태도 표시합니다. 기존 웹훅을 바꾸지 않으며 토큰이나 채팅 ID를 출력하지 않습니다. 두 번째 명령의 날짜·시간은 원하는 이용 조건으로 바꿉니다. 한 날짜의 감시 조건을 중복 없이 DB에 저장하고 첫 수집을 기다립니다.

```bash
.venv/bin/tenniswatch collection-plan
.venv/bin/tenniswatch watch-slots
```

첫 명령은 DB의 수집 계획만 확인합니다. 두 번째 명령은 수집과 알림 발송을 수행하므로 실제 운영에서는 Telegram 메시지가 전송될 수 있습니다.

발송 설정이 있는 `watch-slots`에서 첫 날짜 수집이 성공하면 해당 조건을 `ACTIVE`로 전환합니다. 실패하면 대기 상태를 유지합니다. 수집만 할 때는 `collect-slots`를 사용합니다.

알림 기준은 다음과 같습니다.

- 처음 발견한 예약 가능 상태 또는 마감 후 재개방은 알림 대상입니다.
- 같은 슬롯이 계속 가능하면 기존 사용자에게 반복 발송하지 않습니다. 신규 사용자가 구독하면 현재의 가용 이벤트에 대해 한 번 받을 수 있습니다.
- 겹치는 여러 감시 조건과 기존 구독이 있더라도 이벤트/사용자 단위로 하나의 알림을 저장합니다.
- 특정 날짜·요일·시작 시각 조건과 사용자·시설·사이트의 활성 상태 및 조건 만료를 확인합니다.
- 발송 전에 구독이 해제되거나 슬롯이 마감·재개방되어 기존 이벤트가 낡았다면 취소합니다.
- 관측이 오래됐거나 이후 수집이 실패했다면 이전 상태를 보존하며 발송을 보류합니다. 이용 시작 시각이 지난 알림은 발송하지 않습니다.

## 예약 오픈 알림

```bash
.venv/bin/tenniswatch check-policies
```

이 명령은 **DB에 저장된 정책**을 검사합니다. 강서 사이트의 정책을 자동 수집하거나 사이트의 새 공지를 자동 검증하는 명령은 아닙니다. 현재 규칙 모델은 이용일의 N일 전, 지정된 현지 시각에 열리는 정책을 다룹니다. 월별·공휴일 예외 정책을 임의로 이 규칙에 맞추면 안 됩니다.

검증된 정책이 있고 감시 조건에 맞는 일정을 생성할 수 있을 때 오픈 알림 조건을 활성화합니다. `audience`는 `resident`(지역주민), `general`(일반), `all`(등록된 검증 정책 모두) 중 하나입니다. 같은 시설·대상에 정책 행이 여러 개면 임의로 선택하지 않고 검증을 해제합니다.

정책 출처와 실제 규칙을 운영자가 확인한 경우에만 해당 정책 ID를 지정해 검증 상태를 저장합니다. 예시의 `정책ID`는 실제 숫자로 바꿉니다.

```bash
.venv/bin/tenniswatch verify-policy --policy-id 정책ID
```

확인할 필드는 `facility_id`, `audience`, `open_days_before`, `open_time`, `timezone_name`, `source_url`입니다. 확인하지 못한 실제 예약 규칙을 예시 데이터로 채우지 않습니다. 검사 과정에서 저장된 규칙이 바뀌면 `policy_changes`에 변경 전후를 기록하고, 재검증 전까지 확정 알림을 중단합니다. 발송 직전에도 정책 비교값과 일정 버전을 다시 확인합니다.

알림 창은 겹치지 않습니다.

- 전날 알림: 오픈 24시간 전부터 1시간 전까지, 한 번.
- 1시간 전 알림: 오픈 1시간 전부터 실제 오픈 전까지, 한 번.
- 첫 실행이 오픈 20분 전이라면 1시간 전 알림만 보내며 뒤늦은 전날 알림은 추가하지 않습니다.
- 오픈 시각 이후에는 지난 알림을 보내지 않습니다.

검증 후 일정 시각이 바뀌면 새로운 일정 버전으로 중복 방지 키를 만듭니다. 기존 시각의 대기 알림은 취소합니다. 검증된 정책이 없는 조건은 대기 상태를 유지하며 임의의 확정 시각을 안내하지 않습니다.

## GitHub Actions

- `Availability watch`: 기본 매시 7분, 수집 계획 확인 후 필요한 경우에만 Chromium 설치. 수동 실행에서 `watch-slots` 또는 `send-outbox` 선택.
- `Reservation opening monitor`: 매시 17분, 검증 정책으로 일정과 알림 창 확인. 브라우저 설치 없음. 수동 실행 지원.
- CLI 감시 작업은 공통 PostgreSQL advisory lock으로 겹침을 방지합니다. 발송 대기열은 별도로 `SKIP LOCKED`와 15분 임대, 소유 토큰을 사용합니다.

기본 수집 간격은 DB의 `reservation_sites.poll_minutes`(기본 60분)입니다. GitHub Actions 변수 `WATCH_INTERVAL_MINUTES`가 비어 있으면 사이트 설정을 사용합니다. 이 변수에 `30` 또는 `60`을 지정하면 모든 사이트의 간격을 그 값으로 재정의합니다. robots 규칙과 페이지 조회 간격 제한은 계속 적용됩니다.

30분 감시는 두 설정을 함께 바꿉니다.

1. `watch.yml`의 cron을 `7,37 * * * *`로 변경합니다.
2. Actions 변수 `WATCH_INTERVAL_MINUTES=30`을 설정합니다. 또는 변수를 비우고 개별 사이트 `poll_minutes=30`을 사용합니다.

cron 자체는 저장소 변수로 동적으로 바뀌지 않습니다. [GitHub 공식 일정 실행 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)에 따라 기본 브랜치에 Workflow가 있어야 하고 예약 실행은 지연되거나 누락될 수 있습니다. 정확한 분 단위 도착은 보장하지 않습니다. 두 Workflow의 실행 시간은 합산되며, 브라우저 수집 증가나 30분 변경은 무료 사용량을 초과할 수 있습니다.

## 발송 상태와 복구

| 상태 | 뜻 |
|---|---|
| `PENDING` | 아직 발송하지 않음 |
| `SENDING` | 작업이 임대를 획득함 |
| `RETRY` | 발송 실패 또는 신선도 확인을 기다림 |
| `SENT` | Telegram 성공과 DB 기록 완료 |
| `SKIPPED` | 해제·마감·만료·정책 변경 등으로 취소 |
| `FAILED` | 영구 오류, 잘못된 자료 또는 8회 재시도 소진 |

네트워크·서버 오류는 지수 간격으로 재시도하고 Telegram의 `retry_after`도 지킵니다. 400/401/403/404는 영구 오류로 분류합니다. 403이면 사용자 알림을 비활성화하며, 사용자가 다시 구독 조건을 생성/수정해 동의하면 재활성화됩니다. 데이터 신선도 때문에 보류하는 경우에는 전송 시도 횟수를 소모하지 않습니다.

```bash
.venv/bin/tenniswatch send-outbox
```

이 명령은 실제 발송을 수행하며, 위 검증 규칙을 다시 통과한 알림만 보냅니다. `FAILED` 항목은 원인을 해결한 후 운영자가 선택적으로 재시도 상태로 돌려야 합니다. 발송 성공한 항목을 일괄 초기화하면 중복 메시지가 생길 수 있습니다.

동시 실행과 재시도는 DB 제약과 임대로 줄입니다. 다만 Telegram 전송 성공 직후 DB 기록 전에 프로세스가 중단되면 Telegram에 멱등성 키가 없어 중복 전송 가능성이 남습니다. 구독 해제와 실제 전송 사이에도 짧은 경쟁 구간이 존재합니다.

## 검증과 남은 작업

Python 59개, Worker 25개 모의 테스트와 형식 검사, 문법 검사, `0006`까지 오프라인 마이그레이션 SQL 생성이 통과했습니다. Workflow YAML도 구문 검사를 통과했습니다.

테스트는 첫 관측, 반복 상태, 마감 후 재개방, 신규 구독자, 중복 조건, 날짜/시간/만료, 구독 해제, 수집 실패, 신선도 보류, 발송 재시도, 잠금 소유권 교체, 오픈 알림 창, 지역주민/일반 구분, 정책 변경·미검증·중복 정책과 토큰 비노출을 포함합니다.

실제 PostgreSQL 동시 작업, Supabase 스키마 적용, GitHub 정기 실행, Telegram 수신 및 LLM 대화를 합친 전체 검증은 아직 하지 않았습니다. 실제 사이트 정책 자동 갱신과 월별 예외 규칙도 미지원입니다. 배포·비밀값 등록·전체 수신 점검과 비용 검토는 Phase 7에서 진행합니다.
