# 매일 정해진 시각의 예약 가능 코트 결과

사용자가 요청한 경우에만 기존 잔여석 감시 조건을 묶어 매일 한 번 Telegram으로 보냅니다. 예약 가능한 코트가 없어도 결과를 보내며, 오래된 정보·수집 실패·미수집은 예약 마감과 구분합니다. 이 보고서는 새로운 빈자리 이벤트 알림과 별개입니다.

## 범위와 시각

- 사용자별 한국 시간 `HH:MM` 한 개를 설정합니다. 다른 시간대는 아직 지원하지 않습니다.
- 해당 사용자의 활성·첫 확인 대기 잔여석 감시 조건과 기존 구독을 사용합니다. 오픈 일정 감시는 제외합니다.
- 오늘부터 7일 이내의 이용 날짜와 설정된 시간대만 조회합니다. 특정 날짜의 조건은 날짜가 지나면 매일 새로운 날짜 조건으로 바뀌지 않습니다. 지속적인 보고를 원하면 반복 요일 조건을 등록하세요.
- 감시 조건이 없거나 조회 기간에 해당하지 않으면 그 사실을 안내합니다. 다른 사용자 조건은 조회하지 않습니다.
- 정기 작업은 기본 매시 7분입니다. 설정 시각 이후 처음 실행할 때 발송하므로 최대 약 1시간과 GitHub 실행 지연이 추가될 수 있습니다. 정확한 분 단위 도착은 보장하지 않습니다.
- 등록 시각보다 오늘의 지정 시각이 이미 지났으면 다음 날부터 시작합니다. 지난 날짜 보고서를 소급 발송하지 않습니다.

## 적용 순서

실제 발송 시각이 아직 정해지지 않았으므로 기본 설정을 임의로 활성화하지 않았습니다. 이 기능은 로컬 모의 테스트와 SQL 생성까지 검증했으며 운영 DB 적용·Worker 배포·GitHub 실행·실제 보고 수신은 아직 미검증입니다.

1. 프로젝트 루트에서 `.venv/bin/alembic upgrade head`로 `0008`을 적용합니다. 일정 설정 테이블과 보고서별 중복 방지 키, 인증된 사용자만 관리하는 RPC를 추가합니다.
2. Worker를 `apps/telegram-worker`에서 `npx wrangler deploy`로 배포합니다. Secrets 재등록과 Telegram 웹훅 재등록은 필요하지 않습니다.
3. 봇에 원하는 시각을 포함해 요청합니다. 예: `매일 오후 6시 30분에 기존 감시 조건의 결과를 알려줘`.
4. `매일 결과 알림 설정 알려줘`로 확인하고, 해제하려면 `매일 결과 알림 꺼줘`라고 요청합니다. 도구 이름은 `set_daily_report`, `get_daily_report`, `disable_daily_report`입니다. DB 반영 결과 확인 뒤에만 저장/해제를 안내합니다.
5. GitHub Actions Secrets에 `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`을 등록하고 새 `watch.yml`을 반영합니다. 수집 작업 뒤 보고서 단계를 실행하며, 수집 오류가 있어도 미확인 상태를 구분해서 보고할 수 있습니다. 수동 실행에서 `daily-reports`를 선택하면 수집 없이 DB 관측 기준으로 확인합니다.

로컬 CLI로도 설정할 수 있습니다. 기존 `.env`에 본인 개인 채팅이 연결되어 있어야 합니다.

```bash
.venv/bin/tenniswatch set-daily-report --report-time 18:30
.venv/bin/tenniswatch daily-reports
.venv/bin/tenniswatch disable-daily-report
```

첫 명령은 저장만 합니다. 두 번째는 지정 시각이 된 보고서를 만들고 기존 알림 대기열을 발송하므로 다른 대기 알림도 처리할 수 있습니다. 마지막 명령은 매일 보고만 해제하고 기존 잔여석 감시는 유지합니다. 예시의 18:30은 설명용이며 실제 설정은 사용자 선택 시각을 사용합니다.

## 중복 방지·재시도·데이터 신뢰도

- `daily_report_settings`에 시각·다음 실행 시각·버전·활성 상태를 저장합니다. Telegram ID는 검증된 요청에서만 가져오며 모델이 사용자 ID를 지정할 수 없습니다.
- DB 행 잠금과 사용자·보고 종류·한국 날짜 고유 제약으로 하루 한 건만 만듭니다. 같은 설정을 반복 저장해도 실행 시각을 계속 미루지 않습니다.
- 설정 변경·해제·사용자 비활성·한국 날짜 변경은 발송 직전에 다시 확인합니다. 설정 버전이 달라진 보고서는 취소합니다.
- 기존 outbox 잠금 토큰과 최대 8회 재시도를 재사용합니다. 재시도할 때는 슬롯 상태와 감시 조건을 다시 조회합니다. Telegram 전송 성공 직후 DB 완료 기록 전 중단되는 경우의 중복 가능성은 남습니다.
- 각 슬롯은 사이트 주기의 2배 이내 관측만 사용합니다. 더 최근 수집이 실패/진행 중이면 예약 가능 상태를 확정하지 않습니다. 보고서에 마지막 관측 시각과 링크를 포함합니다.
- 한 보고서에는 최대 8개 예약 가능 슬롯을 넣고 생략 안내를 표시합니다. Telegram 길이 제한에 맞춥니다.
- 보고서 생성·정기 수집·발송에는 LLM을 호출하지 않습니다. 자연어로 설정을 관리할 때만 LLM 호출 한도가 적용됩니다.
- DB 고유 제약·잠금의 실제 PostgreSQL 동시성은 운영 적용 후 검증해야 합니다. 로컬 테스트는 SQLite와 HTTP 모의 자료입니다.

## 로컬 검증 결과

- Python 전체 119개, Worker 전체 59개 테스트 통과.
- TypeScript 타입 검사, Python 문법 검사, `0008`까지 마이그레이션 SQL 생성, Workflow YAML 파싱, Worker 배포 파일 생성 통과.
- PostgreSQL 운영 마이그레이션, 실제 사이트 재수집, 실제 일일 보고 발송, 변경된 GitHub 정기 작업은 아직 검증하지 않았습니다.

## 2026-10-26 운영 점검

Supabase 운영 DB의 `0008` 적용과 일일 보고 시각 저장을 확인했습니다. GitHub Actions Secrets 등록 후 [잔여석 감시 재실행](https://github.com/zmzmgm/TennisWatch/actions/runs/40277833232)에서 수집 1회·관측 3개·오류 0개, 일일 보고 Telegram API 전송 성공 1건·실패 0건을 확인했습니다. 오전 작업은 Secrets 미등록으로 중단됐으므로 보고는 같은 날짜의 재실행 때 늦게 발송됐습니다. 실제 단말 수신은 사용자 확인이 필요합니다.

이 실행에서 psycopg의 INSERT rowcount가 -1로 반환되어 생성 건수가 음수로 기록됐습니다. 전송은 성공했으며 집계는 `RETURNING id`로 실제 삽입된 행을 세도록 수정했습니다. 중복 삽입이 무시되면 0건입니다. 회귀 테스트를 포함한 Python 전체 120개가 통과했습니다.

특정 이용 날짜로 등록한 감시 조건은 날짜가 지나면 더 이상 조회 대상이 아닙니다. 매일 계속 예약 가능 코트를 보고받으려면 반복 요일 조건을 별도로 설정해야 합니다.
